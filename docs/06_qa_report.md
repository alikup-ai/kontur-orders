## 3. Дефекты

### D10 — блокировка теряет связь с отклонением (высокая)
- **Шаги:** карточка KZ-26-101 → «Шаг, стадия, срок» → отметить «Заказ заблокирован», одновременно изменить плановый срок, указать отклонение → «Сохранить».
- **Ожидание:** блокировка ссылается на созданное отклонение (BR-04).
- **Факт:** сохранено, `block_deviation_id` пуст; отклонение записано как «перенос срока»; проверка согласованности сообщает «блокировка без отклонения». То же при возврате стадии.
- **Причина:** ссылка ставилась только если блокировка была *единственным* событием.
- **Исправление:** ссылка ставится всегда при установке блокировки (`domain.apply_changes`).
- **Тесты:** `TestQaRegression::test_d10_*`.

### D11 — закрытие задним числом раньше договора (средняя)
- **Шаги:** заказ на стадии 7 (KZ-26-109) → закрыть датой 31.03.2026 с отклонением.
- **Ожидание:** отказ: дата закрытия не может быть раньше договора и входа в стадию приёмки.
- **Факт:** принято; в истории стадий посещение «закончилось раньше, чем началось»; `validate_order` проверял не все посещения и ошибку пропустил.
- **Исправление:** нижняя граница даты закрытия = max(дата договора, вход в стадию 7); проверка согласованности проверяет каждое посещение.
- **Тесты:** `test_d11_close_date_not_before_contract_or_stage_entry`, `test_d11_validator_checks_every_visit`.

### D12 — срок по договору раньше даты договора (средняя)
- **Шаги:** KZ-26-123 (до договора) → «Подписан договор» сегодня со сроком 5 дней назад.
- **Ожидание:** отказ.
- **Факт:** принято, заказ сразу «Просрочен» — ложная просрочка в показателях.
- **Исправление:** первоначальный и плановый сроки не раньше даты договора, в том числе при сверке срока.
- **Тест:** `test_d12_contract_deadline_not_before_contract`.

### D13 — основной заказ с нулевой выручкой скрывает убыток (высокая)
- **Шаги:** основной заказ: договорная выручка 0, плановая себестоимость 350 000, договор за период.
- **Ожидание:** стоп-сигнал «маржа ниже порога»; убыток −350 000 входит в плановую маржу канала.
- **Факт:** признаков нет («В норме»); заказ выпал из агрегата, и маржа шоурумов **выросла** с 38,8 % до 39,7 %.
- **Причина:** маржинальность при нулевой выручке не определена, поэтому сравнение с порогом не выполнялось; агрегат отбрасывал заказы с нулевой выручкой.
- **Исправление:** у основного заказа нулевая выручка при ненулевой себестоимости даёт признак `low_margin`; агрегат = Σ МД / Σ выручки по всем заказам с данными. Рекламации по-прежнему исключены (BR-27).
- **Тест:** `test_d13_zero_revenue_main_order_flagged_and_counted`.

### D14 — форма молча назначает исполнителя (средняя)
- **Шаги:** KZ-26-106 (нет действия и исполнителя) → поменять только менеджера → «Сохранить».
- **Ожидание:** меняется только менеджер; признак «нет исполнителя» остаётся.
- **Факт:** исполнителем стал ответственный за стадию; в журнале это записано как действие пользователя; показатель «без владельца / шага» улучшился без реального действия.
- **Причина:** форма подставляла ответственного за стадию в поле исполнителя.
- **Исправление:** форма не подставляет значение. Правило BR-21 перенесено в логику: исполнитель по умолчанию = ответственный за стадию **только** когда следующее действие задаётся в этом же сохранении; это видно в журнале.
- **Тесты:** `test_d14_*` (логика и интерфейс); обновлён `test_stage_change_requires_owner_executor_action`.

### D15 — «тихий откат» при работе в двух вкладках (высокая)
- **Шаги:** открыть KZ-26-117 во вкладках A и B. В A сменить менеджера на Седова К. → «Сохранить». В B изменить только следующее действие → «Сохранить».
- **Ожидание:** изменение A не теряется.
- **Факт:** менеджер вернулся к «Гусев П.»: форма B отправила устаревшие значения всех полей. Это хуже, чем заявленное «сохраняется последняя запись»: откатываются поля, которые второй пользователь не трогал.
- **Исправление:** форма запоминает версию заказа на момент открытия. Если к моменту сохранения заказ изменён, сохранение отклоняется с сообщением, поля перечитываются из файла, пользователь вносит правку заново. Многопользовательский режим это не создаёт, но исключает молчаливую потерю данных.
- **Тесты:** `test_d15_two_tabs_no_silent_revert`, `test_d15_own_consecutive_saves_no_false_conflict`.

### D16 — синтетические данные можно принять за реальные (высокая)
- **Шаги:** открыть любой экран и свернуть боковую панель (на телефоне она свёрнута по умолчанию); или сделать скриншот основной области.
- **Ожидание:** на каждом экране видно, что данные синтетические.
- **Факт:** метка была только в боковой панели; заголовок вкладки «Контур заказов» без пометки. Скриншот: `screenshot-1792227259325-3.jpg`.
- **Исправление:** плашка «Демонстрация на синтетических данных (набор от …). Числа ниже — не показатели компании» вверху основной области каждого экрана; заголовок вкладки «Контур заказов · ДЕМО».
- **Подтверждение:** `test_d16_synthetic_label_in_main_area_on_every_page`; браузер, панель свёрнута: `screenshot-1792227580453-4.jpg`.

### D17 — поздно закрытые заказы без подтверждённой причины не видны (средняя)
- **Шаги:** главный экран; KZ-26-122 закрыт за период позже срока, причина не подтверждена.
- **Ожидание:** руководитель видит, какие причины подтвердить на совещании (критерий B5).
- **Факт:** закрытые заказы в список не попадают; показатель «срывы с подтверждённой причиной: 1 из 5» есть, а списка «что подтверждать» нет.
- **Исправление:** на главном экране раздел «Закрыты с нарушением срока — причина не подтверждена» (закрытые за 28 дней, последнее отклонение не подтверждено). Раздел исчезает после подтверждения.
- **Тесты:** `test_d17_closed_late_unconfirmed` (логика), `test_d17_closed_late_unconfirmed_section` (интерфейс).

### D18 — одинаковая подпись, разные числа (низкая)
- **Шаги:** главный экран «Под риском — 7» → панель «Под риском 8».
- **Факт:** список группирует по главному состоянию, панель считает заказ во всех состояниях (KZ-26-114 просрочен, заблокирован и под риском). Без пояснения это выглядит как ошибка.
- **Исправление:** пояснение на главном экране, показатель на панели переименован в «Под риском (все)».
- **Тест:** `test_d18_list_explains_difference_with_dashboard`.

### D19 — несколько снимков за день (низкая)
- **Шаги:** панель → «Зафиксировать неделю» дважды.
- **Факт:** два снимка одной даты; сравнение «с прошлым снимком» становится сравнением с самим собой.
- **Исправление:** второй снимок за день отклоняется с сообщением.
- **Тест:** `test_d19_one_snapshot_per_day`.

### D20 — неизвестно, на сколько нарушен срок закрытого заказа (низкая)
- **Факт:** карточка показывала «Закрыт с нарушением первоначального срока» без числа дней, хотя система его считает.
- **Исправление:** «… на 16 дн.».
- **Тест:** `test_d20_closed_late_shows_days`.

## 6. Заявленные ограничения и замечания руководителя производства (не дефекты)

| Замечание | Оценка |
|---|---|
| Фактические затраты не ведутся: перерасход на переделке не увидеть | Заявленное ограничение v1 (§8.3 дизайна). Интерфейс говорит об этом прямо (Q07). Без пообъектного учёта затрат вводить факт вручную бессмысленно |
| «Статус обновлён» можно освежить, сдвинув срок действия на день | Не предотвратить программно. Закрывается выборочной сверкой B6 и разбором на совещании |
| Мастер в цеху не будет заполнять форму из шести полей, тем более без телефона | Реалистично: данные будет вносить менеджер заказа или мастер участка за компьютером. Риск для B3 — проверить на пилоте |
| Исполнитель не получает уведомления | Узнаёт из списка и на совещании. Уведомления — этап 2 |
| Подтвердить причину может любой | Нет авторизации (заявлено). Подтверждение — решение совещания, кто нажимает — видно в журнале, но не проверено |
| Новое имя в поле «ответственный» с опечаткой создаст «другого человека» | Справочник сотрудников — этап 2 вместе с авторизацией |
| Загрузка производства не видна | Гипотеза H3 проверяется ретроспективой, не инструментом (ревью §3) |
| Перенос срока на более ранний тоже требует отклонения | Осознанное правило: любое изменение срока клиенту объясняется |
| Два пользователя одновременно | Многопользовательский режим не поддерживается (заявлено); после D15 потеря данных заменена явным конфликтом |
| Если в демо-набор внести реальные заказы, плашка «синтетические» останется, а сброс их удалит | Консервативно для демонстрации; для пилота нужен отдельный файл данных без демо-набора (этап 2: импорт) |
| Синтетические показатели не доказывают ничего о компании | Плашка на каждом экране после D16; аудит §6 перечисляет, что нельзя оценить без реальной истории |
